# Adding and changing skills

## The shape of this repository

```
skills/<name>/SKILL.md        one folder per skill; nothing else is a skill
skills/<name>/references/     detail the skill reads only when a step needs it
skills/<name>/scripts/        optional helpers; every step must also work without them
bin/, src/                    the installer (no run-time dependencies)
scripts/                      validate, build, new-skill, check-docs
.claude-plugin/marketplace.json   generated by npm run build
```

Every skill stands alone. A skill may say "if the `agentrail-x` skill is
installed, use it; otherwise …", but must never need another skill: harnesses
have no way to install or call one skill from another, and Claude.ai uploads
one skill at a time. See [docs/harnesses.md](docs/harnesses.md).

## Add a skill

```sh
npm install
npm run new-skill -- agentrail-<job>     # e.g. agentrail-fix-readiness
# write skills/agentrail-<job>/SKILL.md and its references
npm run build                            # updates the marketplace and the README table
npm run check                            # build is current, every skill is valid, tests pass
```

Then try it in at least two harnesses (Claude Code and Codex, say) and with a
small model, with prompts a real person would type. Note what you tried in the
pull request.

## Rules for a skill

`scripts/validate.mjs` enforces the ones a machine can check.

- **One job per skill**, named `agentrail-<job>`. The description says what it
  does, then "Use when …" with the words a request would use, then "Not for …"
  naming the nearest other skill's job, so two skills never compete.
- **Frontmatter** only: `name`, `description`, `license`, `compatibility`,
  `metadata` (all values quoted strings, including `version`). `name` and
  `description` on one line each.
- **SKILL.md under 500 lines.** It holds the order of the work and the rules.
  Detail goes in `references/`, one level deep, each file saying when to read
  it. A reference over 100 lines starts with `## Contents`.
- **Write for any model and any harness.** Plain imperative steps. Say "run",
  "ask the person", "read the file", never a harness's tool names. Say what to
  do when there is no shell. Give each step a check that proves it worked.
- **Take facts from the product, not from memory.** Each reference names the
  live guide it follows (its `.md` address). Add the words and code it relies
  on to `scripts/docs-anchors.json`, so `npm run check:docs` notices when the
  docs change.
- **Secrets never pass through the chat.** Tell the person where to put them,
  and read them from the environment.
- **Ask before changing anything** the person owns: packages, code, deploys,
  scans, anything that spends money.

## Releasing

1. Bump `version` in `package.json`, and `metadata.version` of each skill that
   changed. Run `npm run build`.
2. Merge to `main`. `npx github:agentrail-co/agentrail-skills` serves `main`.
3. Tag `vX.Y.Z` and push the tag. The release workflow checks the commit,
   attaches a ZIP of each skill to a GitHub release (for Claude.ai and Claude
   Desktop), and publishes the package to npm once a maintainer approves the
   `npm` environment run in GitHub Actions. npm trusts that workflow and
   environment, so no npm token is stored anywhere, and every version carries
   provenance. A version with a hyphen (`0.2.0-dev.1`) goes to npm's `next`
   tag and is a GitHub pre-release.
